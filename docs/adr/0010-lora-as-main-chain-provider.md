# ADR 0010：本地微调模型（LoRA）作为主链路的 provider，而不是旁路脚本

- 状态：已接受
- 日期：2026-11-19
- 相关代码：`framework/lora_format.py`（提示词格式单一真源）、`framework/lora_engine.py`（本地运行时）、`framework/ai_engine.py`（`_request_model` / `_request_lora` 路由）、`framework/config.py`（`LORA_*`）、`framework/core.py`（`set_lora_config` / `lora_status_text`）、`ui/ui_manager.py`（设置界面分组）、`ui/pet_window.py`（接线）、`finetune/train_lora.py`、`finetune/inference.py`、`tests/test_lora_engine.py`
- 相关 ADR：[0005 能力开关运行期可翻且必须落盘](0005-runtime-capability-switches.md)、[0002 技能重放零模型调用](0002-skill-replay-zero-llm.md)、[0004 可验证执行](0004-verifiable-execution.md)

## 背景

本项目有一条硬规矩：**桌面对话主链路只认 `framework/core.py`**，旁路能力必须在 README 的「能力 / 边界对照」里显式标出「不塞进主链路」。LoRA 微调此前就属于后者：`finetune/` 下是 31 条样本的训练脚本与一个命令行推理脚本，训出的适配器**没有任何一条代码路径**能让产品用上——README 里那行「独立训练脚本，未接入产品推理链路」是实话。

问题不在于「训不出模型」，而在于**接不上**：微调产物是一套本地权重，而主链路唯一的推理出口是 `framework/ai_engine.py` 里那个走 HTTPS 的 DeepSeek 调用。HTTP 接口接不住本地 PEFT 适配器，于是这条能力天然落在主链路之外。

把它接进主链路，有三个必须先想清楚的问题：

1. **接在哪一层？** 接在 `core.py` 里等于给动作链加一条特殊分支；接在 `ai_engine.py` 里则是给「要模型」这件事加一个 provider——后者不改动任何动作语义，撤销账本、质量门、计划流全都不动。
2. **训练与推理的提示词格式一致吗？** 微调最常见的失败是「训的是 A、跑的是 B」：训练脚本与推理脚本各写一遍模板，只要一处改了格式，效果就莫名其妙地差，而且**不会报错**。原来的 `finetune/train_lora.py` 与 `finetune/inference.py` 就各写了一份字面量。
3. **本地模型答不好怎么办？** 一个 1.5B 的模型不会每次都吐出合规的动作 JSON。如果把它的输出直接塞进动作队列，用户会看到半截 JSON；如果一概拒绝，那本地通路等于白接。

## 决策

### 1. 接在 `ai_engine.py`：加一个 provider，不加一条动作分支

`AIWorker` 的取答案入口从 `_request_deepseek()` 改成 `_request_model()`，路由顺序：

```
本地微调（config.LORA_ENABLED 开启时） → 云端模型（DeepSeek） → 离线规则兜底
```

本地通路返回的动作列表与云端返回的**同一种东西**（`list[dict]` 动作序列），下游完全不变：动作解析、计划卡确认、撤销账本、质量门一行都不用改。这也是本项目一贯的做法——新增能力接在「统一入口」上，而不是在调用点堆分支（见 ADR 0005：调用点数量会长大，漏改一处就出现「显示关闭、实际在跑」）。

### 2. 提示词格式只有一处：`framework/lora_format.py`

训练脚本（`finetune/train_lora.py`）、命令行推理（`finetune/inference.py`）、产品推理（`framework/lora_engine.py`）全部从这一个模块取模板，模板字面量只允许出现在这一个文件里。这条由契约检查钉死：训练脚本里再出现 `### 指令：` 就红。

顺带修掉一个真缺陷：原训练脚本 `enc["labels"] = enc["input_ids"].copy()` 让**提示部分也参与 loss**，等于让模型连提示一起背，而推理时只喂提示——训练目标与推理用法对不上。现在提示段掩成 `-100`，只有回答部分参与训练。

### 3. 「答不好就退云端」要有可判定的规则

本地输出按下面三档处理（`ai_engine._request_lora`）：

| 本地输出 | 判定 | 动作 |
|---|---|---|
| 合法的动作 JSON 数组，且至少一个动作在动作池里 | 合格 | 用它，照常执行 |
| 明显是想吐 JSON 却吐坏了（以 `{`/`[` 开头、剥掉 markdown 围栏后仍解析失败） | 不合格 | 退给云端；云端没配 Key 再退离线规则 |
| 确实是一段人话（不是 JSON） | 当回答收下 | 包成 `show_bubble` 显示 |

最后一条是有意的：本地模型被训的是「输出动作 JSON」，但它也可能是**在跟你说话**。把这种人话判成「不合格」会让本地通路在闲聊场景下毫无用处；而把吐坏的 JSON 当人话显示，则是欺骗用户——两者的区别就是「它到底想吐 JSON 吗」，上面第三条规则用「首字符是不是 JSON 开头」来判。

另外两条硬规矩：本地通路**只吃当前这一句用户输入**（长期记忆 / 检索资料 / 人设提示词不进本地模型——1.5B 的模型吃不下，也不该假装它记得）；本地推理**抛异常时退给云端**，不许拖垮主链路。

### 4. 依赖是可选的，默认关闭，状态如实可见

`torch / transformers / peft` 只在 `requirements-finetune.txt` 里，主链路**顶层不 import 它们**（运行时模块里也是懒加载），没装这些包的机器完全不受影响。`LORA_ENABLED` 默认 `False`：这是产品行为的变化，默认不该变。

可用性由 `lora_engine.status()` 如实报告（缺依赖 / 缺权重 / 就绪三种），设置界面上有开关、基座模型、适配器路径、设备四栏，外加一个「测试加载」按钮——真的加载一次，把结果说清楚。适配器路径的判据是「目录里有没有 `adapter_config.json`」：光有目录不算数，那说明不了它是训练出来的适配器。

### 5. 能力边界照旧写在明处

接进主链路**不等于**能力变大。README 的对照表里这一行写的是：

> LoRA 微调 | 桌面主链路（可选 provider） | `framework/lora_engine.py` 是主链路的**第一个 provider**：开关打开后先问本地基座+适配器，答得不合动作协议就退给云端；只吃当前这一句用户输入；缺依赖 / 缺权重时如实降级，不假装答了

## 怎么证明

| 层次 | 手段 | 断言 |
|---|---|---|
| 静态接线 | `tools/check_contracts.py`（CI 步骤，110/110） | 训练脚本与推理脚本都 `from framework import lora_format`，且两边都不许再有 `### 指令：` 字面量；`ai_engine` 有 `_request_model` / `_request_lora` 且 `_request_model` 排在 `_request_deepseek` 之前；本地输出不合协议时确实退云端（`不合协议` + `normalize_action`）；运行时模块顶层没有 torch/peft/transformers 导入，主依赖清单里也没有这三个包；开关与路径落盘（`lora_enabled` 等四个键 + `set_lora_config`）；设置界面四个控件与两个信号都真接线 |
| 单元行为 | `tests/test_lora_engine.py`（25 项） | 模板与历史训练格式逐字一致；训练集出现过的指令前缀推理端都能生成；训练脚本不再自带模板且提示段掩成 `-100`；缺依赖 / 缺适配器时 `status()` 如实报告且 `load()` 抛可读原因；推理只 decode 新生成的 token（不含提示）；贪心解码默认开；本地优先时**根本不调用**云端；吐坏 JSON / 非法动作 / 推理抛异常三种情况都退给云端；人话输出被当回答收下；没开本地时走原来的云端；设置界面四个控件能勾能填、存盘时真把值发出去；配置存—读回环；`Framework.set_lora_config` 落盘且状态文案正确 |

| 真实窗口手动 | `docs/QUICK_START.md` 断言 14 | 设置界面勾上开关、填适配器路径、「测试加载」的回报与真实原因一致；关掉后对话回到云端模型 |

## 代价

- **多一个 provider 就多一处会出错的地方**：本地推理慢（CPU 上 1.5B 每轮几秒到几十秒）、可能答不合协议。代价由「不合协议就退云端」和「异常就退云端」两条兜底买断，代价是每轮多一次调用与一次判定。
- **本地模型只覆盖窄场景**：训练集 31 条样本覆盖的是「一句话 → 动作序列」这类短指令。文档生成、联网调研这类需要长上下文的活儿，本地模型答不了，会退回云端——这是如实，不是缺陷。
- **训练脚本改了格式口径**：提示段掩码改变了训练目标，此前若有适配器是用老口径训的，重训一次即可（31 条样本，成本很低）。提示词模板本身逐字未变，历史权重仍然对得上。
- **适配器权重不进仓库**：`finetune/output/` 已加进 `.gitignore`（几十上百 MB 的二进制），训练数据仍入库以便复现。

## 补充（2026-11-20）：真训一次，四处断点

前文的接线做完后，开关能开、状态能报，但 `finetune/output` 里没有任何权重——
那条链路实际上从未跑过一次真实推理。这次把它真跑通了，暴露出四个只在
「真训练」时才会显形的问题。

### 1. transformers 5.x 移除了训练脚本依赖的三个参数

`TrainingArguments(warmup_ratio=...)` 在 5.x 里被删除（只剩 `warmup_steps`），
`Trainer(tokenizer=...)` 改名为 `processing_class`，`from_pretrained(torch_dtype=)`
改为 `dtype=`。三处任一没改，脚本一启动就 TypeError。`requirements-finetune.txt`
原来锁的是 `transformers>=4.40,<5.0`，与实际验证环境（5.19）不一致，一并校准。

### 2. 训练步数在 31 条样本上根本算不过来

原配置 batch 4 × 累积 4 × 3 轮 = **6 步**，连 warmup 都摊不开。改成 batch 2 ×
累积 4 × 40 轮 = 160 步；`max_length` 从 512 降到 192（实测样本 max 160 token，
512 有三分之二花在 padding）。32 步与 160 步的差距见下表——同一份数据、同一条
评测，动作全对从 12.9% 到 96.8%。

### 3. 受限网络下 `from_pretrained` 连缓存齐全都加载不了

本机 huggingface.co 被代理拦（502），而 `from_pretrained` 默认先发元数据请求校验
缓存，请求失败即抛错，**哪怕权重已完整落在本地**。新增
`lora_engine.from_pretrained_cached()`：先 `local_files_only=True`，失败再联网。
训练脚本与命令行推理共用这一份逻辑（单测钉住「先本地、后联网」的调用顺序）。

### 4. 指令前缀的「猜」与训练集标注不一致

`lora_format` 曾按「像不像提问」决定前缀用「用户问：」还是「用户说：」。核对 31 条
标注后发现 4 条猜反：「在吗？」「我的画图工具在哪里？」「你今天都干了啥？」三条带
问号却标「用户说：」，「你是谁？介绍一下自己。」标的是「用户问：」。等于推理端发出
的提示与训练分布相反——又一次「训的是 A、跑的是 B」。前缀本身不携带语义（模型要
理解的是冒号后面那句），改为恒定 `用户说：`、训练集统一，并由单测逐条比对
「推理端拼出来的指令 == 训练集标注」。

### 实测口径（真实权重，非 mock）

| 口径 | 可用 | 动作全对 | 参数全对 | 平均耗时 |
|---|---|---|---|---|
| 训练集 31 条（32 步旧配置） | 38.7% | 12.9% | 12.9% | 10.90 s |
| 训练集 31 条（160 步） | 100% | 96.8% | 96.8% | 2.12 s |
| holdout 10 条（未参与训练） | 90% | 60.0% | 50.0% | 3.80 s |

评测脚本 `tools/eval_lora.py` 走的就是主链路的判定函数（`AIWorker._request_lora`），
不另写一套标准；holdout 是人工构造的同义改写（`finetune/data/holdout.jsonl`），
参数名按动作池真实协议写（`set_volume.volume`、`remind.text/seconds`、`remember.fact`），
写错参数名会让「参数全对」变成假数字。

**结论要诚实**：96.8% 是训练集内分数，说明「学进去了」；60% 是泛化分数，说明 31 条
样本只覆盖词面——换成「把待办清单打开看看」就吐出动作池里不存在的 `open_task_list`，
被协议判成不合规退回云端。这两个数字必须并列展示，只报前者就是自欺。
