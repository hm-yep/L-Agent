# 0007 · 跨端共用一条授权通道（桌面锚点 + 回环兜底）

- 状态：已采纳（2026-11-17）；2026-11-18 补「四条真断与由此定下的不变量」
- 相关：`framework/grant_anchor.py`、`framework/grant_service.py`、`framework/core.py`、`ui/grant_card.py`、`api/server.py`、`api/static/index.html`、`tests/test_grant_chain.py`、[ADR 0006](0006-session-path-grants.md)

## 背景

F2 把桌面侧的文件读取改成了三态判定：根外路径要用户点一次头，授权两档、只活在本次进程里。接下来网页调试台也要读本机路径，要求「不分治」：在浏览器里点「允许整个文件夹」，切回桌宠读同目录的另一个文件，不能再弹一次卡。

先核实了一个容易想当然的前提：

- `python main.py --api` 确实在**同一进程**里用后台线程跑 uvicorn，但那个 API 并没有持有 `Framework`，它只有自己的 `_memory` / `_tasks`；
- README 与 Docker 镜像还单独跑 `uvicorn api.server:app`，那是**独立进程**，里面没有 Qt、没有桌宠、也没有 `Framework`。

所以「同进程共享一个 GrantStore 单例」这个方案只对第一种启动方式成立，对 Docker / 独立 API 直接失效。要是两种部署各写一套判定，就会出现两套授权记录、两套超时规则、两套按钮语义——正是这次要消灭的分治。

## 决策

**桌面进程是唯一锚点（anchor），网页端只当客户端；判定与状态机只有一份实现，进程边界只影响「记录归谁保管」。**

1. 桌面侧用标准库 `http.server.ThreadingHTTPServer` 起一个只监听 `127.0.0.1` 的小服务，端口由系统分配；把 `host` / `port` / 一次性令牌 / `pid` / 启动时刻写进本机发现文件 `grant_anchor.json`。发现文件里**没有任何路径**——授权记录仍然只在内存里，重启必然回到默认拒绝（沿用 ADR 0006）。
2. 网页端 `GrantAnchorClient` 先查发现文件。找到锚点，就把 `ask` / `answer` / `state` / `revoke` 四件事全部转交给桌面进程，答案落在桌面那份 `GrantService` 里；前端 `/grant/{gid}` 只是这条通道的 HTTP 外壳。
3. 找不到锚点（桌宠没开、Docker 里根本没装 Qt）时，网页端用**同一个 `GrantService` 类**自持：判定逻辑、两档授权、120 秒按拒、文案口径完全一样，只是授权记录归网页端自己保管。绝不伪造一个「已授权」来蒙混过关。
4. 锚点每次请求都校验 `X-Grant-Token`，用 `secrets.compare_digest` 比对；令牌每次启动重生成，旧发现文件自然失效。`GrantAnchorClient` 的 `discover()` 只认同时有 `port` 与 `token` 的文件，缺一即当作没有锚点。
5. `POST /chat` 与 `POST /agent/run` 遇到 `grant` 时**立即返回** `pending_grant`，不阻塞等用户点；前端显示确认条，三个按钮分别回 `file` / `tree` / `deny`。`/grant/{gid}` 继承 app 级 `require_access`，配了令牌必须带令牌、没配令牌只接受回环，不存在匿名可达的后门。
6. 120 秒没答，`GrantService.expire_due()` 把请求标记成 `timed_out=True` 且 `decision=deny`，下一次响应通过 `grant_note` 明说「按拒绝处理了」——不把超时伪装成用户主动拒绝。

## 为什么这样设计

- **不分治的定义是「同一份记录 + 同一套判据」**，不是「两个进程各跑一份一样的代码就凑合」。锚点让桌面成为唯一的授权保管者，所以杀手级验收（浏览器点 tree → 桌面同目录不再弹卡）在两种启动方式下都成立。
- **不用 WebSocket / 不引入新依赖**：授权是低频、短请求，回环 HTTP + 发现文件足够；Docker 镜像里没有 PyQt5 也能 import 这两个模块（它们只依赖标准库）。
- **自持模式是降级而不是分裂**：桌宠关掉时网页端仍可用，授权只在网页端生效；桌宠再开起来时不会继承网页端的临时授权——这是可以接受的代价，比「把授权落盘以跨进程共享」安全得多。落盘会让 ADR 0006 里被明确否决的长期敞口回来。

## 代价与边界

- 锚点不可达时网页端每次请求要多做一次发现文件读取 + 一次失败的回环连接（超时 5 秒）；实测只在桌宠没开时出现。
- 发现文件放在本机应用数据目录，依赖文件权限挡住其他本机用户；进程内令牌避免了同机其他程序随便调用锚点，但如果本机已被攻陷，这一层本来也挡不住。
- 自持模式下网页端与桌面端的授权互不相通，UI 必须如实说明「当前没有桌宠锚点，授权只在这个网页服务里有效」。
- 超时是**按拒绝**，不是放行：宁可让用户多点一次，也不让一个没人应答的弹窗变成静默放行的口子。

## 2026-11-18 复测：通道通了，链路是断的

514 项测试全绿证明的是**判据与协议**（三态、两档、超时、鉴权、`pending_grant` 字段），没有证明**动作链真的能续跑**。真机跑一遍就暴露四条：

1. **网页点「允许」会被改写成「拒绝」**。`GrantCard.closeEvent` 对没答过的卡片补发 `deny` 是对的（关卡＝不读），但卡片被程序关闭时也照发；`answer()` 之后紧接着关闭，于是网页刚生效的 `file` 档被这条后到的 `deny` 覆盖，暂存的动作链整条丢掉。
2. **并发两条请求只有一张卡**。`GrantCard` 单例复用，第二条把第一条覆盖，第一条永远答不了——桌面侧看起来「卡住了」。
3. **恢复队列不认归属**。只有一个 `self._grant_queue`，任何一条请求答复都会把这份队列当成自己那份恢复；而且网页端发起的请求根本没有暂存，也不该碰桌面链路。
4. **点一下授权按钮桌宠直接消失**。`GrantService.get()` 返回的是 `PendingGrant` 对象不是字典，槽里按字典读 `info.get("timed_out")` 抛 `AttributeError`；PyQt 对信号槽里的未捕获异常是**直接 abort 进程**（退出码 127，连 traceback 都不打），所以这个 bug 在测试里表现为「测试文件整个消失」而不是「一条用例失败」。

由此定下两条不变量，后续改动必须守住：

- **一条请求一份归属**：授权相关的每张卡、每份暂存队列都以 `gid` 为键；卡片被关闭时的补发拒绝只在「这条请求还没被回答过」时发生（`GrantService.answer()` 用 `newly` 告知调用方），恢复动作链时只恢复自己 `gid` 那份，`gid` 不在桌面上暂存过就一步都不动。
- **Qt 槽不许让进程死掉**：任何由信号触发的收尾函数都要兜住异常，兜不住时也要把「我没读到」如实说出来——静默消失对用户等于「它坏了」，比说错一句更糟。`GrantService.get()` 返回对象而非字典是这类误用的源头，读它的字段一律用属性。

## 验证

- `tests/test_grant_chain.py`（11 项）钉死真实链路：驱动真实 `Framework` 进程 + 真实 `GrantCard` + 真实回环锚点，不喂打桩应答。覆盖上述四条各自的症状（网页允许不被改写、两张卡都能答且两个文件都真被读、网页请求不动桌面队列、答过期 gid 吃不掉别人的队列、关卡恰好补发一次拒绝、超时按超时播报、槽里抛异常不 abort、`PendingGrant` 不许当字典读）。
- `tests/test_api_grant.py` 钉死七个场景：`file` 档不溢出到同目录另一个文件；浏览器点 tree 落到桌面锚点；重启后还要再问；deny 不因同目录已有授权而变 allow；超时按拒并在下一次响应说明；`/grant/{gid}` 鉴权与 decision 校验；`/agent/run` 同样返回 `pending_grant`。
- `tools/check_contracts.py` 检查锚点只绑回环、令牌用 `compare_digest`、发现文件不含路径字段、两个响应模型都带 `pending_grant`、`/grant/{gid}` 在 app 级鉴权之下；另钉三条：一条请求一张卡且队列按 gid 归还、已答过的卡片关闭不再补发拒绝（`mark_resolved` 有调用方）、授权收尾槽有兜异常外壳且不把 `PendingGrant` 当字典读。
- 人工验收见 [QUICK_START 断言 11](../QUICK_START.md) 第 7 步（两张卡叠着都能点、关卡后网页点允许仍生效）。
