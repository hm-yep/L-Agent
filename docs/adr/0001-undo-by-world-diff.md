# ADR 0001：撤销按「世界快照求差集」实现，而不是逐动作逆操作

- 状态：已接受
- 日期：2026-11-15
- 相关代码：`framework/effect_journal.py`、`framework/core.py`（`_begin_turn` / `_finish_turn` / `_do_undo_last`）、`tests/test_effect_journal.py`、`tools/check_contracts.py`
- 相关 ADR：[0002 技能重放零模型调用](0002-skill-replay-zero-llm.md)

## 背景

桌面对话链路一轮可能跑多个动作：调音量、加待办、划掉待办、记事实、生成交付文件、开应用、锁屏……用户说一句「撤销」，期望的是这台电脑回到本轮开工前的样子，而不是听模型说一句「已经撤销」。

难点在于「一轮干了什么」没有天然的清单。动作执行器分布在十几个 `_do_*` 分支里，还穿插着技能重放（一次 `run_skill` 展开成一串动作）、后台线程、模型返回迟到等情形。如果撤销逻辑依赖「我记得我执行过哪些动作」，它就必须和执行器保持同步，而执行器是会改的。

还有一条硬约束：撤销要能在离线、无模型、API 欠费的条件下工作。它不能是「把上一轮对话再发给模型，让模型生成一份撤销计划」。所以撤销的判据必须是纯数据、纯本地、可离线单测的。

## 备选方案

### 方案 A：每个动作手写一段 undo

在 `_do_set_volume` 旁边写 `_undo_set_volume`，在 `_do_todo_add` 旁边写 `_undo_todo_add`；执行时把 undo 压进栈，撤销时逐个弹栈。

**失败模式**：判据散落到十几个分支里。新增一个动作、或者给现有动作加一个参数分支（例如 `set_volume` 带 `app` 时调的是某个应用自己的会话音量），只要漏写一处 undo，用户就会看到「撤销成功」而世界没变回去。更麻烦的是这种漏写没有测试能发现：单测只会覆盖写了 undo 的那些动作，漏掉的那一处恰好不在测试里。执行器和撤销器是两份各自维护的真相，必然漂移。技能重放还会往一份 undo 栈里塞进一串动态展开的动作，放大这个风险。

### 方案 B：事务日志（WAL / 操作日志）

把所有副作用先记成日志条目（「把音量从 80 改到 30」「添加待办 X」），提交时回放，撤销时按日志反向补偿。

**失败模式**：它要求每个副作用都走同一个写入口。现实是这些状态分散在 `TaskBoard`、`MemorySystem`、交付清单、系统音量接口和真实文件系统里，有的还是外部进程状态（应用窗口、电源计划）。把它们全部收编进一个事务层，等于先重写整个执行器。而且日志记的是「我们以为自己做了什么」，不是「世界实际变成了什么」——某个动作执行到一半抛异常、或外部程序自己改了音量，日志和世界就对不上，反向补偿会补出一个不存在的状态。这跟方案 A 是同一类问题：真相来自意图，而不是观测。

### 方案 C：每轮开工拍世界快照，收口求差集

只定义五个可观测面：音量、待办、提醒、交付文件、长期记忆（`WORLD_KEYS`）。每轮开工读一次，收口再读一次，两次归一后求差集；差集就是「这一轮在这台电脑上真的改了什么」，逆操作由差集生成，不由动作清单生成。

**代价与失败模式**：只看得见这五个面。开了程序、锁了屏、截了图、另起一轮工作流这类后果，快照里没有，无法回退。若把「看不见」当成「没发生」，就会静默地撤不干净——这恰好是最危险的失败模式。本方案把这部分显式列成 `BLIND_SPOTS`，撤销时逐条念给用户（见「诚实性设计」）。另外，快照要求读操作无副作用、可重复，且归一化稳定（提醒按身份而非时间戳比较，待办保留 done 位），否则 diff 会抖动。

## 决策

采用方案 C，流程固定为四步：

1. **开工拍快照**：`_begin_turn` 时读一次 `normalize(...)` 记为 `before`，同时记下本轮开始时间。
2. **收口求差集**：本轮动作跑完，`diff(before, snapshot())` 得到回退项列表；`blind_spots(动作名)` 得到快照看不见的后果清单。二者一起存进 `_last_undo`，撤销一次后即销账，避免「撤销撤销」套娃。
3. **按差集执行逆操作**：`undo_ops` 只取可逆项；`apply_ops` 按 `_UNDO_ORDER` 的固定优先级执行（volume → fact → reminder → todo_done → todo_add → delivery），不是按时间序，因为时间戳只有部分对象有。删文件前还有四道关卡：开关、后缀白名单、大小上限、以及文件 mtime 必须晚于本轮开始时间（不是本轮生成的用户文件一律不动）。单项失败不中断整串回退。
4. **撤完再求一次差集自证**：重新 `diff(before, snapshot())`，剩下的差集就是「没撤成」的项，逐条报出；不拿「逆操作执行过了」冒充「世界已经回去了」。

判据只有 `effect_journal.py` 这一份。动作实现改了什么，快照就看见什么，两者不会漂移；`run_skill` 展开出来的动作不需要为撤销做任何特殊处理，因为它们造成的效果同样落在五个可观测面里。该模块零模型调用、零 Qt 依赖，纯函数 + 纯数据，可用假手（假 `api`）离线单测。

## 后果

### 分类账：8 / 15 / 1 / 6 / 0

`coverage(VALID_ACTIONS)` 把 30 个动作分进五个桶，当前结果：

| 桶 | 数量 | 含义 |
|---|---|---|
| reversible | 8 | 改了可观测面，能按差集回退 |
| no_effect | 15 | 只改界面/姿态或只读，本来就不用撤 |
| undo | 1 | `undo_last` 自己，避免递归记账 |
| blind（明确不可逆） | 6 | 有后果但快照看不见，当场说明 |
| unknown | 0 | 未分类，视为错误 |

`blind` 里的 6 个是动作池里的动作名；`BLIND_SPOTS` 表里还有一条 `set_volume_app`，那是 `set_volume` 带 `app` 参数时的轨迹别名，不是独立的池内动作，所以分类账总数仍是 30。

### 「新增动作忘了归类」比「分类分错」更常见

这是反复踩过的坑：分类表写错一项，人工评审多半能看出来；但新增一个动作却忘了把它放进任何一张表，代码照常跑、撤销照常「成功」，只是这个动作的效果永远不会被回退，也不会被说成撤不回——它悄悄落进 `unknown`。所以 `coverage()` 把 `unknown` 单列成一个桶，并要求调用方把它当错误处理，而不是当空值忽略。

这条约束由两层保证：

- **单测**（`tests/test_effect_journal.py::TestCoverage`）：`test_every_action_is_classified` 断言 `coverage(VALID_ACTIONS)["unknown"] == []`；`test_three_buckets_partition_the_action_pool` 断言四个桶加起来正好等于 `len(VALID_ACTIONS)`；`test_no_action_is_counted_twice` 断言没有动作被重复归类。动作池一加新动作而分类表没跟上，这几条立刻红灯。`tools/test_agent_features.py` 里也有一条相同断言，把约束带进手动自检。
- **CI 契约检查**（`tools/check_contracts.py`）：CI 依次跑 pytest 单测、契约检查、157 项集成自检与评测集。契约检查把「动作契约单一真源」（`framework/action_registry.py`）与撤销分类覆盖对齐，任何新增动作没登记或没归类都在流水线里失败，而不是等到用户说「撤销」时才暴露。

### 诚实性：撤不干净就如实说没撤成

「可逆」在这里是一个覆盖率声明，不是一个态度声明。设计上做了三件事：

1. **看不见的不假装没事**：`blind_spots()` 返回动作名 + 人话原因，例如「程序我已经帮你打开了，但我不替你关——你窗口里可能有你没存的活儿」「锁屏之后没法替你解锁」。撤销时这些原因逐条念给用户，而不是笼统一句「已撤销」。
2. **执行结果不等于撤销结果**：`apply_ops` 每一项都返回 `{"op", "ok", "note", "label"}`，某只手抛异常或返回失败就记 `ok=False` 并附原因，且继续撤后面的项——撤到一半整个停摆，比撤得少更难收拾。
3. **自证 + 如实措辞**：撤完重读世界求一次差集，剩余项就是没撤成；气泡文案用「退回 N 项 / 没撤成 M 项」，明细卡片把每项标成 `[可撤]` 或 `[撤不回]`。

代价是承认边界：这套机制只覆盖五个可观测面，6 个明确不可逆的动作以及所有快照看不见的副作用都不在承诺范围内。把边界写清楚，比把它藏起来更有用——用户据此才知道哪些操作要自己留意。
