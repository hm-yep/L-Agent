# 评测（Evaluation）

本目录放两套评测的落盘产物。CI 每次运行都会用 `--md` / `--json` 重新生成并以此为卡口，因此这里的内容始终与代码当前状态一致，不是手写快照。

## 两套评测各测什么（口径差异）

| | `tools/eval_tasks.py` | `tools/benchmark.py` |
| --- | --- | --- |
| 产物 | [capability.md](capability.md) | [benchmark.md](benchmark.md) |
| 测什么 | **端到端能力覆盖**：用户吩咐的事，基础链路能不能办成（动作池 / 必填表 / 别名归一 / 质量门 / 计划 / 文档 / 表格 / 搜索） | **扰动下的可靠性 + 进化是否真的有用**：同一条任务跑「学习前 / 学习后」两臂 |
| 期望结果 | 全过（这是能力健全的底线，满分不丢人） | **有区分度**：学习后完成率显著高于学习前，且如实保留若干硬失败 |
| 任务规模 | 38 条 · 6 组 | 32 条 · 10 类扰动 |
| 失败样本 | 0（能力项应全过） | 6 条硬失败保留（缺参 / 恶意动作 / 计划冲突 / 零重合资料） |
| CI 卡口 | 通过率 ≥ 阈值（默认 100%） | 完成率 ≥ 0.8 **且** 提升 ≥ 10pp **且** 救回 ≥ 4 条 |

**一句话区分**：`capability` 回答「基础能力健全吗」（满分是好事）；`benchmark` 回答「在扰动下把事办成、且进化不是摆设吗」（有 +25pp 的区分度，硬失败保留不刷满分）。

## 为什么「离线」是优点而不是缺点

两套评测都是**确定性离线链路**（零真实 LLM 调用），跑一次 1~5 秒、结果可复现、进 CI 当卡口不会抖动。它量化的是**项目自己写的机制**（规则归纳、偏好记忆、质量门、计划 DAG、撤销账本）有没有真的起作用——这是可以离线证明的。

它**不**回答的是「真实大模型下的完成率 / 越权拦截率 / token 消耗」。这是一条**有意的边界**，不是被遗忘的缺口：真实模型有随机性（本项目 `temperature=0.9`）、要花真金白银、Key 不能进 CI，所以它不可能成为可复现的回归卡口。离线臂证明「机制是对的」，在线臂要回答的是「机制 + 模型合起来，对真实用户的话完成率到底多少」——两者口径不同，不能互相替代。

## 在线臂（Online Arm，尚未实现，边界自白）

面试若追问「那真实大模型下完成率多少」，正确回答是**分两层**，而不是含糊：

1. **离线臂已答的部分**：扰动下的机制可靠性、进化是否真的有用（+25pp），这是可离线证明的。
2. **在线臂要答的部分**：真实模型 + 真实机制合起来，端到端完成率。这条**没做**，且刻意没做——因为它与离线臂是正交的、不可复现的、要钱的。

在线臂的**最小落地方案**（复用 `framework/ai_engine.py` 里已有的 `_request_deepseek` 真实调用链，不另起炉灶）：

- 复用 `tools/benchmark.py` 的 32 条 `utterance`，把「预置动作序列」替换成「真实 DeepSeek 返回的动作序列」，其余链路（`parse_actions → check_pre → quality_gate → plan_graph`）原样复用；
- 每条采样 n 次（如 n=3）标注方差，报告 `mean ± std` 完成率、越权拦截率、平均 token/延迟；
- 需要 `DEEPSEEK_API_KEY`（不进 CI、不进 git），作为手动一次性脚本 `tools/benchmark_online.py --api-key <key> --n 3` 单独跑，结果落到 `docs/eval/online-<date>.md`，与离线报告并列标注口径。

这一条是本项目明确的「下一阶段」边界，README 评测区块已如实注明，不把它包装成已完成的深度。

## 趋势

`tools/benchmark.py --append-history` 会把每次运行的学习前/后完成率追加到 `docs/eval/history.jsonl`（与本目录其余报告同路径），用于长期趋势跟踪（防止某次改动悄悄把进化能力改坏，`--min-delta` 就是这道卡口）。CI 每轮把该文件连同各报告一起作为 workflow artifact 上传（`eval-artifacts`），因为 runner 是一次性的、不落盘历史就会随其销毁；仓库内提交一份种子历史作基线，趋势对比 = 种子基线 + 历次 artifact。
